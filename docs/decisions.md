# Implementation decisions

Updated 2026-10-18 (Asia/Tashkent).

- Work directly in the requested Git checkout. No commits, pushes, or external publication were made.
- Keep code small and direct: no recursive config inheritance, custom CLI wrappers or unused future-phase schemas/settings. Experiment files override fields from the default config; later features add their configuration when implemented. The CLI handles errors once at its entry point, and parser/index identities share one implementation. Run IDs use standard UUIDs.
- Python 3.13.1, `src` packaging, `uv.lock`, Pydantic, YAML, PyMuPDF, SQLite, and persistent Chroma form the Phase 0–2 implementation. Exact transitive versions are pinned by the lockfile. No orchestration framework is needed for a fixed baseline.
- Generation uses Claude Haiku 5.5 (`claude-haiku-5-5`) through the Anthropic SDK. A small live structured-output call passed. Embeddings use Voyage 4 Large at 2048 dimensions through the official SDK, with the same model for documents and queries. This prioritizes retrieval quality for a small scientific corpus and keeps experimental comparisons consistent. The configured key routes to MongoDB Atlas; small embedding and rerank-3 calls succeeded. The initial trial throughput limit was resolved after the user added a payment method; the historical 657-chunk index and saved-index reuse passed. The new 40-paper / 1,158-chunk Voyage-tokenized build also passed: 683,346 embedding tokens over 37 calls in 34.77 seconds. See [model setup](models.md).
- Course-rubric and video requirements are removed. Preserve the existing 20 papers and add 20 selected papers for the agreed 40-paper corpus. Acquisition, reparsing, indexing and evaluation will proceed interactively with the user running each command and returning its output.
- MCP is outside implementation scope. The agent will use direct retrieval function calls; an external-client MCP wrapper is only a possible future extension.
- Failure reports include actual observed failures and limitations, with no minimum count and no deliberately induced project failures. Negative questions test successful abstention.
- Credentials are read from environment variables or the ignored project `.env`. `doctor --live` checks Atlas embeddings/reranking and Claude generation; `doctor` makes no API calls.
- Embedding cache keys include provider identity, model, dimensions, tokenizer, chunk ID and text. Versioned indexes include PDF hashes, parse IDs, metadata fingerprints and chunk fingerprints. Active indexes are selected only after a complete build; a completed index is reused without mutation.
- Use fixed chunks capped at 600 tokens with a 100-token overlap target for B0. The official `voyageai/voyage-4-large` tokenizer is pinned to revision `bb931c2635a93efe400c24741363d8ff61d7bb32` and loaded locally through `tokenizers`, replacing `tiktoken`/`cl100k_base`. Its character offsets replace custom UTF-8 byte-offset conversion. Chunk text is recounted at new boundaries to enforce the cap; whole-character adjustments can slightly reduce overlap. Query limits and evidence-text budgets use the same tokenizer. Provider API usage remains the source for model-specific tokens/costs. The historical results retain their original tokenizer; reparse, verify/rebind source annotations and rebuild before new runs. Chunks can cross section/page boundaries; evidence returns every contributing section and page. BM25, section-aware chunking, hierarchy expansion, graph traversal and the direct-function agent remain later phases.
- A `Block` retains extracted original text and a compact character mapping through whitespace cleanup/dehyphenation. Source spans are half-open Unicode character offsets into that original text. PDF pages are 1-based; printed page labels are additional metadata. These are extraction offsets, not byte positions in the PDF file.
- PyMuPDF reading order is corrected for common two-column layouts and wide separators. Numbered small-cap headings are supported. Uncertain front matter gets an explicit fallback section. These are heuristics and require sampling; no claim of perfect semantic structure is made.
- The first 40-paper run exposed six `few_detected_headings` warnings. Parser v4 adds Roman-numbered small-cap headings and splits named heading lines merged with prose, preserving labels/titles on the same line. The fix passes targeted checks and 43 offline tests; the full corrected run now has 47,592 blocks, 955 sections and 1,158 chunks with no diagnostic warnings. All 26 original benchmark passages match unique current blocks with identical raw text, page/bounding box and quote offsets. The one-off migration checked both splits before updating IDs; the user applied it, canonical validation passed and the new held-out freeze is valid. Independent verification confirms that all other annotation fields are unchanged. The new dense index is complete; vector IDs, 2,048-dimensional finite/nonzero vectors, chunk fingerprints and benchmark source spans all passed local verification. Both five-question development runs passed with exact shared candidates. Gold-span P@5 changed from 0.16 to 0.28 and group recall from 0.467 to 0.80; semantic support is assessed separately. A correct equation followed by an opposite-sign verbal description in reranked dev03 is recorded as an observed answer issue. Dense held-out execution is complete: all 15 questions passed execution/source checks, with abstention on both designated unanswerables. The paired reranked test also completed all 15 questions with exact shared candidates, unchanged settings/prompt and abstention on both designated negatives. Held-out P@5 changed 0.1077→0.2154, group recall 0.4103→0.8077 and complete coverage 5/13→10/13. An exploratory assistant review of all 40 answers assigns held-out requested-point relevance 1.77→1.85 on a 0–2 rubric; this is not independent human grading or exhaustive correctness/support auditing. Reranking fixes test11 coverage but drops Ditto in test13; test05 lacks FedAvg in the initial pool. No prompt or parameter was changed after observing held-out outputs. No warnings are suppressed to make a run pass.
- Keep original table/equation blocks in canonical documents, but exclude detected table cells and equation-like fragments from baseline chunks. Horizontal-rule tables below captions are flagged even when PyMuPDF's default table detection misses them. Captions can provide prose evidence; chart pixels and unvalidated numeric cells are not interpreted. Some borderless tables or equations can evade detection.
- All 40 PDFs exist locally and pass checksum validation; the original 20 manifest entries are preserved. The manifest keeps only paper ID, title, year, source URL, document version, SHA-256 and method names. Corpus download/search commands remain outside the application CLI. Baseline retrieval searches all chunks unless the caller supplies a filter; automatic paper routing and query rewriting are disabled.
- A shared `RetrievalService` validates filters, enforces candidate/evidence budgets, and removes substantial overlapping source spans. It records dense cosine scores and, when enabled, separate reranker relevance scores; neither is treated as a calibrated answerability probability. The generator judges sufficiency from the packed evidence; no arbitrary similarity threshold is claimed to solve abstention.
- Structured claims cite known evidence IDs. Code checks citation existence and source provenance; semantic claim support, answer correctness, and abstention require review. An unknown citation rejects the answer instead of silently repairing it. No agent planner is involved.
- Benchmark annotations are selected directly from canonical source blocks, independently of retrieval. Exact quotes and raw character spans are validated without a dense index or API credential. Held-out execution requires a frozen file hash after source verification; the freeze records whether independent human review occurred. Automated span-overlap metrics remain diagnostics until required-fact matches have been adjudicated.
- USD cost fields remain null unless the user supplies deployment pricing. Usage token counts and request counts are recorded. No rate-limit, cost, or quality claim is made without live measurements.

Documentation consulted: [Claude Haiku 5.5](https://platform.claude.com/docs/en/models/haiku-5-5/overview), [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [Voyage embeddings](https://docs.voyageai.com/docs/embeddings), [Chroma clients](https://docs.trychroma.com/reference/python/client), and [PyMuPDF text extraction](https://pymupdf.readthedocs.io/en/latest/recipes-text.html).

- Document every source/test function, marking small supporting functions with `Helper to ...:`. The README Python file guide explains each real module and its purpose. Temporary `docs/` notes will be consolidated into the README/final reports and removed in Phase 8.

- The first live development answers added unnecessary theory/proof qualifications. The answer prompt was refined once to focus on requested facts and assess sufficiency against the question; the earlier and final run identities are retained in the evaluation report. Held-out labels/questions were not used for this change.
- `evaluate --candidate-source` now supports this directly: it verifies the B0 source index, label hash, split, question IDs, prompt and settings, then reuses exact candidate IDs/order/scores through the shared retrieval/answer workflow. Replay skips query embedding/search and records its source-run hash and timing scope. Integration checks reproduce all five real B0 evidence lists without model calls; 50 offline tests pass, including incompatible-source rejection.
- Initial B0-R diagnostics replay the exact saved B0 candidates, with identical IDs/order/scores, so query-time retrieval variation does not confound the reranking check. These are five-question development span diagnostics; semantic quality still requires adjudication.
- Evaluation reports explicitly describe the fast Chroma/Voyage retriever, its 20-candidate cap, shared deduplication, optional `rerank-3` ordering of all remaining candidates, and final up-to-five/4,000-token selection. Include the tokenizer/revision and distinguish final evidence count from the reranker's output count.
