# Model setup

Generation uses **Claude Haiku 5.5** (`claude-haiku-5-5`) through the official Anthropic SDK. Embeddings use **Voyage 4 Large** (`voyage-4-large`) through the official Voyage SDK, with **2048-dimensional float vectors** for both document chunks and questions. Optional reranking uses **`rerank-3`**. The same embedding/generation models stay fixed across controlled retrieval comparisons.

Set both keys in the ignored project `.env`:

```dotenv
ANTHROPIC_API_KEY=your-claude-key
VOYAGE_API_KEY=your-voyage-key
```

`FEDRESEARCH_GENERATION_MODEL` and `FEDRESEARCH_EMBEDDING_MODEL` optionally override YAML model names. Dimensions, batch size, timeouts and SDK retries are in `configs/default.yaml`. `doctor` reports configuration/key presence without sending requests; `doctor --live` makes small embedding, reranking and structured-generation calls. Both keys are now present. Atlas embedding and reranking calls succeeded; the current key routes to `https://ai.mongodb.com/v1` automatically through the official SDK.

Voyage embeds passages with `input_type="document"` and questions with `input_type="query"`. Silent truncation is disabled, and vector count, dimensions and finite/nonzero values are checked. The API enforces its 32,000-token per-input and 120,000-token per-request limits. The default batches contain 32 short chunks.

Since 2026-10-16, chunking, stored passage-token counts and query-length checks use the official `voyageai/voyage-4-large` tokenizer at revision `bb931c2635a93efe400c24741363d8ff61d7bb32`, replacing `cl100k_base`. The lightweight `tokenizers` library loads its approximately 7 MB JSON file from Hugging Face and caches it locally; no model weights, Transformers/PyTorch runtime or API key are needed. Padding/truncation are disabled, and offsets refer to Unicode characters. The 600-token chunk cap is checked again on each actual chunk; overlap targets 100 tokens with adjustments at whole-character boundaries. The 4,000-token evidence budget counts passage text only and excludes citation labels/prompt formatting. Claude uses its own tokenizer; actual Voyage/reranker/Claude usage is recorded from each API, rather than inferred from this text budget. [Official tokenization guide](https://www.mongodb.com/docs/voyageai/tutorials/tokenization/)

Claude requests the `GeneratedAnswer` Pydantic schema with `messages.parse()`. Refusals, incomplete outputs and unknown citation IDs are rejected. The live CLI check on 2026-10-15 returned a valid insufficient-evidence answer: 551 input tokens and 70 output tokens. This verifies generation access/schema parsing, not corpus retrieval quality. Both adapters sanitize provider errors to type/status.

`evaluate --candidate-source <B0-run.json>` reuses the saved B0 candidate pool without query-embedding or dense-search calls. Reranking and nonempty-evidence Claude calls still run normally; their own API usage is recorded. Query embedding/search usage and latency remain in the source run. Query vectors are held temporarily in memory for Chroma search and are not saved in `run.json`; candidate IDs/cosine scores and query-embedding token/request usage are saved. All final selected evidence chunks are included in the Claude payload, regardless of which chunks the answer later cites. No model or prompt was changed for this comparison.

Reranking is off in `configs/default.yaml` and `b0_dense.yaml`. `b0_dense_rerank.yaml` enables it on the same dense candidates. The existing `retrieval.candidate_limit` bounds both modes (20 by default). Both modes deduplicate original source spans before the optional ranking stage and share the final item/token budgets. The trace preserves original/reranked ranks and scores, source IDs, latency and token usage; provider failures remain failures. Truncation is disabled. [Atlas reranker documentation](https://www.mongodb.com/docs/voyageai/models/rerankers/?client=python)
